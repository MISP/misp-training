\section{Explore the knowledge base}

\begin{frame}{A large, reusable body of knowledge}
\begin{itemize}
\item 136 Galaxy definitions and 136 cluster collections.
\item 58,528 entries; 56,551 distinct cluster UUIDs.
\item 79,372 listed directed relationship edges.
\end{itemize}
\note{Measured from the pinned checkout by the supplied offline explorer. These are entries and edges, not counts of distinct threat actors, verified claims or records visible to every MISP user. Collections can overlap and reuse UUIDs, including different ATT\&CK views. Pin the revision when comparing results.}
\end{frame}

\begin{frame}{Start with the public catalogue}
\begin{itemize}
\item Browse \url{https://www.misp-galaxy.org/}.
\item Follow JSON and original-source references.
\item Inspect collection scope, authors, version and status.
\end{itemize}
\note{The public knowledge-base website does not require a MISP instance. The source repository is the reproducible machine-readable reference. A local MISP installation can have a different database/import revision from the website or your checkout; distinguish those when debugging missing knowledge.}
\end{frame}

\begin{frame}{Choose a family that answers the question}
\begin{itemize}
\item ATT\&CK: observed techniques, software and activity groups.
\item D3FEND and preventive measures: defensive context.
\item DISARM: information-manipulation techniques and responses.
\item Country, sector, detection and other domain knowledge.
\end{itemize}
\note{The repository covers substantially more than actor and malware lists. Prefer domain-specific ATT\&CK collections when appropriate; the combined collection contains broad and historical material. The README links selected catalogue families rather than embedding an unmaintainable exhaustive list.}
\end{frame}

\begin{frame}{Galaxy, cluster and element}
\begin{itemize}
\item Galaxy: the family and its presentation metadata.
\item Cluster: one named concept with an individual UUID.
\item Element: metadata such as synonyms, references or external IDs.
\end{itemize}
\note{The repository has galaxies/name.json definitions and clusters/name.json collections. A collection contains a values array of individual cluster entries. Its UUID is not the UUID of each entry. Family and collection are associated by type; do not assume their UUID fields are interchangeable.}
\end{frame}

\begin{frame}{Context is different from incident data}
\begin{itemize}
\item Taxonomy: classification vocabulary.
\item MISP object: grouped typed attributes.
\item Galaxy cluster: structured knowledge attached as context.
\end{itemize}
\note{Attaching an actor cluster is an analytical assertion, not a technical indicator or proof of causation. Object references, value correlations and analyst-data relationships have different purposes. Use the taxonomy and object-template courses for those models.}
\end{frame}

An attachment does not create a cluster-to-cluster edge.
\note{A cluster-to-cluster edge describes knowledge independently of a particular event. An event association says the selected concept is relevant to that event. Taxonomy tags can qualify a relationship without being the relationship's identity. Source, direction and evidential scope need separate review.}
\end{frame}

\begin{frame}{Search for identity, not just a familiar label}
\begin{itemize}
\item Compare values, synonyms and external identifiers.
\item Retain cluster UUID and collection provenance.
\item Do not merge identities solely because names overlap.
\end{itemize}
\note{Synonyms support discovery; they do not prove a one-to-one mapping between providers. Attribution labels can overlap or be disputed. The explorer returns candidates, not an entity-resolution decision. Use original sources, scope and uncertainty to choose among candidates.}
\end{frame}

\begin{frame}{Check whether the entry is current}
\begin{itemize}
\item Read original references and collection version.
\item Inspect revoked flags, deprecation metadata and historical descriptions.
\item Check ATT\&CK domain, platform and technique/sub-technique scope.
\end{itemize}
\note{Historical knowledge can be valuable without representing the current preferred concept. A successful search is not proof that an entry is active. The combined ATT\&CK collection includes historical material, so the workshop uses an enterprise-specific collection and an external identifier.}
\end{frame}

\section{Apply context in MISP 2.5}

\begin{frame}{Choose the narrowest justified attachment}
\begin{itemize}
\item Event scope describes the incident or report as a whole.
\item Attribute scope can express a narrower observation.
\item Verify the actual attachment after saving and exporting.
\end{itemize}
\note{Parent context can appear in attribute exports without being directly attached at attribute level. Current bulk attachment supports optional attribute-to-event mirroring when enabled; that broader scope can change the assertion. Explain why the whole event supports the concept before mirroring.}
\end{frame}

\begin{frame}{Use the installed cluster metadata}
\begin{itemize}
\item Search and inspect the cluster before attaching it.
\item MISP maintains a cluster-associated tag.
\item Prefer UUID-backed identity over manually constructed labels.
\end{itemize}
\note{Imported default tag names commonly look like misp-galaxy:type="value". Custom knowledge and naming conventions need not match every imported default. Use the actual metadata supplied by the instance rather than treating a guessed tag string as a complete, accessible cluster definition.}
\end{frame}

\begin{frame}{Keep visibility boundaries separate}
\begin{itemize}
\item Event visibility controls incident access.
\item Custom-cluster distribution controls knowledge access.
\item Local attachment controls the association scope.
\item Publication and sync settings control eligible sharing.
\end{itemize}
\note{A local-only Galaxy also restricts non-local attachments. Attaching a private cluster does not automatically grant recipients access to its definition. The API checks both target permissions and cluster visibility. A cluster relation and an event attachment are different operations with different permissions.}
\end{frame}

\begin{frame}{Matrix highlights are observations, not coverage}
\begin{itemize}
\item Galaxy ordering defines matrix tabs and columns.
\item Cluster kill-chain metadata places entries in that layout.
\item A highlight does not establish detection or prevention efficacy.
\end{itemize}
\note{The galaxy kill\_chain\_order and cluster meta.kill\_chain must use matching keys/prefixes. Interpret the selected domain/platform and source revision. Separate observed technique, available detection, tested detection and effective prevention. A matrix is not an attribution-confidence or maturity score.}
\end{frame}

\begin{frame}{Read graph edges as sourced assertions}
\begin{itemize}
\item Inspect direction, relationship type and references.
\item Review confidence or handling tags where supplied.
\item Do not infer causality merely from a graph path.
\end{itemize}
\note{Relations may span collections and point to concepts absent from a restricted local view. An unresolved target does not establish identity equivalence. Do not copy every knowledge-base relation into the evidential claims of an incident.}
\end{frame}

\begin{frame}{Custom clusters and forks are supported}
\begin{itemize}
\item Create permitted custom knowledge with explicit ownership.
\item Fork a default cluster for local analysis.
\item Record provenance, distribution and publication intent.
\end{itemize}
\note{Default imported clusters are protected from normal edits. The reviewed fork workflow records extends\_uuid and extends\_version while creating separate custom identity. Forking is not automatic agreement with future upstream changes. Normal editing and publication require appropriate permissions, including Galaxy-editor privileges where applicable.}
\end{frame}

\begin{frame}{Updating files is different from updating the catalogue}
\begin{itemize}
\item Select and update the intended Git revision.
\item Import/update the MISP database through the operator workflow.
\item Review changed knowledge and custom forks before sharing.
\end{itemize}
\note{The model reads app/files/misp-galaxy. Admin updateGalaxies imports from disk; it does not fetch Git. Avoid force/wipe operations as a routine exercise. Custom cluster synchronisation depends on publication, permissions, sharing groups and peer settings; forwarding a tag alone is not complete knowledge distribution.}
\end{frame}

\section{Explore, validate and contribute}

\begin{frame}[fragile]{Explore a pinned checkout offline}
\begin{lstlisting}
python3 examples/explore.py /tmp/misp-galaxy-lab --stats
python3 examples/explore.py /tmp/misp-galaxy-lab \
  --search T1059 \
  --collection mitre-enterprise-attack-attack-pattern \
  --limit 3
\end{lstlisting}
\note{Clone and check out the reviewed revision first; full commands are in the README. The explorer is standard-library Python, needs no API key and makes no network calls. It searches value, synonyms and external\_id, with a result bound. It prints provenance and raw metadata to support source review.}
\end{frame}

\begin{frame}[fragile]{Repository structure: family versus collection}
\begin{lstlisting}
galaxies/training-knowledge.json
  type, namespace, name, uuid, version, description

clusters/training-knowledge.json
  type, name, uuid, version, source, authors, category
  values: [individual cluster entries]
\end{lstlisting}
\note{This is a file-layout illustration, not an API payload. The supplied galaxy.json and clusters.json are valid standalone repository-format examples. A private MISP cluster API export can have a different envelope. Match family and collection type and preserve the distinction between family, collection and individual identities.}
\end{frame}

\begin{frame}[fragile]{An individual cluster can reference another}
\begin{lstlisting}
{
  "value": "Training observation A",
  "uuid": "<individual cluster UUID>",
  "meta": {"synonyms": ["Workshop A"]},
  "related": [{
    "dest-uuid": "<cluster B UUID>",
    "type": "related-to", "tags": []
  }]
}
\end{lstlisting}
\note{The angle-bracket UUIDs illustrate the structure and must not be submitted as data. The executable fixture contains real generated UUIDs. Relationships need meaningful types, correct direction and resolvable targets under an explicit policy. Schema success alone does not establish all those semantics.}
\end{frame}

\begin{frame}{Validate more than JSON syntax}
\begin{itemize}
\item Check both repository schemas.
\item Check identities, matching types and relationship targets.
\item Exercise negative cases and inspect original sources.
\end{itemize}
\note{The verifier checks the synthetic fixture and four negative cases: mismatched type, dangling target, duplicate fixture UUID and blank label. It also performs a real ATT\&CK lookup and tests empty/unknown collection cases. Fixture references are internal; real cross-collection knowledge needs a broader target-resolution policy.}
\end{frame}

\begin{frame}{Workshop: find, assess, attach}
\begin{itemize}
\item Find a technique by external identifier and read its evidence.
\item Compare a synonym search and a domain-specific collection.
\item Attach to a disposable event; compare attribute and local scope.
\item Inspect matrix/export results and remove training data.
\end{itemize}
\note{The optional live lab uses an unpublished organisation-only event and an authorised user. Fork only when permitted, keep custom knowledge restricted and compare visibility with a second ordinary user. This update validates offline exercises and audits server source; it does not claim new live-server or screenshot testing.}
\end{frame}

\begin{frame}{Contribute at the correct source}
\begin{itemize}
\item Manual collection: edit JSON with evidence and provenance.
\item Generated collection: inspect the generator and upstream source.
\item Preserve identities and update relevant versions.
\end{itemize}
\note{CONTRIBUTE.md distinguishes generated ATT\&CK knowledge from manually maintained collections. Prefer original references. For threat-actor data, cfr-* metadata needs CFR evidence and attribution-confidence has a specific country-of-origin meaning. Do not treat it as universal confidence in an incident attachment.}
\end{frame}

\begin{frame}[fragile]{Follow the current upstream validation workflow}
\begin{lstlisting}
./jq_all_the_things.sh
# Review and commit intended normalised changes.
./validate_all.sh
\end{lstlisting}
\note{Use a dedicated checkout with jq, moreutils/sponge and the current Python validation dependencies. Formatting can rewrite many files. The reviewed CI also uses PyMISPGalaxies tests and compares the generated README index. The course verifier is not a substitute for that complete pipeline.}
\end{frame}

\begin{frame}{Make knowledge reusable and reviewable}
\begin{itemize}
\item State source, identity, meaning and uncertainty.
\item Keep attachment scope separate from knowledge distribution.
\item Include reproducible examples and validation limits.
\item Use the README for pinned references and workshop commands.
\end{itemize}
\note{The earlier lesson, images and published PDF remain archived outside standard training. The new course points to the large live knowledge base and pins the reviewed snapshot for reproducibility. Repository counts and schema checks do not prove the truth or completeness of every entry.}
\end{frame}
